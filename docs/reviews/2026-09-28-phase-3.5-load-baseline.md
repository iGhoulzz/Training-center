# Phase 3.5 load baseline — 2026-09-28

This is a repeatable measurement of four staff flows, not a build threshold or a production latency promise. The protocol-level k6 harness and exact rerun steps are in [`tests/Load/README.md`](../../tests/Load/README.md). Login is excluded because Filament throttles it; 20 independently minted staff sessions were reused instead.

## Target and method

- Code under test: `703232f` (`p35/t11-load-baseline`) in the isolated `docker/dev-linux/` workspace. The post-run session-cleanup API refactor does not alter any measured application endpoint or k6 script.
- Docker Desktop 29.8.0 on WSL2 Linux x86-64, 16 available vCPUs and 7.61 GiB available memory. App container: PHP 8.4.25 and Laravel's CLI development server with `PHP_CLI_SERVER_WORKERS=8` (`--no-reload`); no container CPU or memory quota. Database: MySQL 8.4.7. Queue: Redis 8.4.0 with Horizon running. Generator: `grafana/k6:1.4.0` on the same Docker network.
- Actual app configuration on `training_center_performance`: queue `redis`, cache `database`, sessions `database`, session lifetime 480 minutes. This is the disposable performance database, separate from the Linux test database and the Windows test database; no development or production data was targeted.
- Fixture: T05 `seed:performance-dataset --profile=medium` on a freshly rebuilt database: 4,000 students/enrolments/charges, 8,000 payments/allocations, including the required 4,000 charges and 8,000 allocations. The seeded owner completed the normal staff-panel password rotation before minting 20 independent sessions.
- Each script ran sequentially at 20 virtual users for five minutes. Search and reports used the untouched fixture; enrol-and-collect ran next and appended data; receipt downloads use PDFs created by that flow. `flow_duration` covers the full application flow per iteration, including failed iterations. Throughput below is **successful flows divided by the fixed 300-second window**, not k6's rate over its extra graceful-drain seconds. HTTP p95 and HTTP error rate include every request in the flow.

## Correctness and limits

Search required the seeded `PERF-000100` hit in the Livewire response. Each report iteration checked both its applied filters and report-specific rendered fixture data. Enrol-and-collect used Filament's actual quick-create action, then verified the new bill's derived paid amount rather than accepting an HTTP 200 as proof of payment.

The write run began with 4,000 students, enrolments and charges, and 8,000 payments and allocations. It ended with 6,821 students/enrolments/charges and 10,770 payments/allocations. Thus all 2,821 attempts created the provisional student, enrolment and charge, while exactly the 2,770 successful flows created a payment and allocation. All 51 failed flows got HTTP 500 during `finalize`: the application log records MySQL `SQLSTATE[40001]` / error 1213 deadlocks on `payment_allocations` insertion from `RecordPaymentAction`. This is an observed concurrency failure for follow-up work, not a k6 assertion gap or a claim that this task fixes payment locking.

All 2,770 successful collection payments acquired a receipt path and PDF before the download run, with zero queued or reserved jobs and zero `failed_jobs` rows. The download script used 20 distinct payment IDs whose paths and files were checked first; gaps in the IDs came from rolled-back payment inserts during failed finalizations. It received 238 PDF responses and two HTTP 500 responses, **not** 429s. Both 500s correspond to application-log MySQL error 1213 deadlocks in `Illuminate\Cache\RateLimiter` while inserting into the database cache table. This is distinct from the payment-allocation deadlock above. During the receipt-job drain, mPDF also logged PHP's 128 MiB memory exhaustion; all 2,770 PDFs eventually appeared, but the worker memory headroom merits follow-up. Queue delay was not measured by this task.

Receipt throughput is limiter-shaped: all 20 sessions belong to one user, and the route allows 60 requests/minute per user. The script sleeps 25 seconds per VU after every attempt, including failures; that pacing is outside `flow_duration`. It measures successful PDF delivery within the limiter, not unthrottled endpoint capacity. The 20 signed load sessions were revoked after the run: session rows fell from 22 to 2, and the private manifest was removed.

The target is a local Docker development server, not the production web stack or host. Its result can ground the next SLO discussion but must not be projected onto an unmeasured VPS. An initial search attempt was discarded after another checkout replaced the shared app container mid-run; the table uses only the clean, uninterrupted rerun after rebuilding the disposable target.

## T15 closing note — the payment-allocation deadlock, rerun 2026-09-29

This section is appended, not a correction. Everything above is T11's measurement and stands as written; only the enrol-and-collect flow was rerun, so the other three rows of the table are untouched and were not re-measured.

Same target and same method: the `docker/dev-linux/` workspace on Docker 29.8.0, MySQL 8.4.7, PHP 8.4.25 with `PHP_CLI_SERVER_WORKERS=8`, Laravel 13.30.1, queue `redis` with Horizon running, cache `database`, sessions `database` with `SESSION_LIFETIME=480` — all four drivers read back from the running configuration rather than assumed. The medium fixture was rebuilt to 4,000 students/enrolments/charges and 8,000 payments/allocations before **each** run below, and each ran at 20 VUs for five minutes against 20 freshly minted sessions, revoked afterwards.

| Run | Code under test | Flow errors | Successful flows | Flow p95 | Successful flows/s | HTTP p95 | HTTP error rate |
|---|---|---:|---:|---:|---:|---:|---:|
| T11 baseline, 2026-09-28 | `703232f`, no retry | 51 / 2,821 (1.80%) | 2,770 | 11,001 ms | 9.23 | 388 ms | 51 / 16,875 (0.30%) |
| T15, three attempts | `c9e8853` | 1 / 2,657 (0.038%) | 2,656 | 11,600 ms | 8.85 | 454 ms | 1 / 15,941 (0.006%) |
| T15, five attempts | `87cb45d` | **0 / 2,764 (0%)** | 2,764 | 11,260 ms | 9.21 | 412 ms | **0 / 16,584 (0%)** |

Row deltas validate each figure independently of k6. The three-attempt run took students, enrolments and charges from 4,000 to 6,657 — all 2,657 attempts — while payments and allocations went from 8,000 to 10,656, exactly the 2,656 successes and not one row more. The five-attempt run took charges to 6,764 and payments and allocations to 10,764: +2,764 on both sides, every attempt collected. A retry that had re-recorded a committed payment would show as payments exceeding successful flows, and neither run does.

**The deadlock did not go away, and the fix does not claim it did.** `SHOW ENGINE INNODB STATUS` was read during both runs and reports the lock set T11 recorded, unchanged: both transactions holding `lock_mode X` on the **supremum** of `payment_allocations_charge_id_index`, both then waiting for `insert intention` on that same gap. The last detection in the five-attempt run is timestamped `2026-09-29 09:40:53`, eighteen seconds before the run ended, on the allocation insert for charge 6747. What changed is that the loser survives it: the application log holds no `SQLSTATE[40001]` entry from that run at all, against 51 from T11's.

**Three attempts was not enough, and the reason is worth recording.** The first bound came from arithmetic — 1.80% per attempt, cubed, is one flow in 170,000 — which predicted 0.015 failures across 2,657 flows. One occurred, and the log names it as the same 1213 on the allocation insert after all three attempts were spent. That is enough to reject the arithmetic: a single failure is a 1-in-70 event if the attempts really were independent. The mechanism is not mysterious — Laravel retries immediately, so a loser restarts into the same gap while the other nineteen sessions are still in it.

**What that one failure does not support is a rate, and none is given here.** An earlier draft of this note solved back from it to a conditional loss of about 14% per retry and projected a residual near one flow in 128,000. Both numbers were extrapolations from a single event, resting on two unmeasured assumptions — that the first-attempt rate was still 1.80% under the changed code, and that the conditional probability is constant across retries — and they are withdrawn. Five attempts is the setting whose rerun measured zero, not a value derived from a validated model.

**What the zero run does support.** Zero failures in 2,764 flows bounds the post-fix rate below roughly **0.11%** by the rule of three (one-sided, 95%), and no more tightly than that — a zero count cannot distinguish "rare" from "never" on this sample. Against T11's 1.80%, whose own interval is 1.35%–2.37%, the improvement is established at better than twelvefold; its true size is not measured, and a run of this length could not measure it.

**A clean run is not a proof of zero.** Retrying makes this failure rare; it cannot make it unreachable, because every attempt takes the same gap lock again. The one construction that would remove the conflict outright is running the collection transaction under READ COMMITTED, where InnoDB takes no gap locks — a change to the isolation level of the money path, and an owner decision rather than something a bug fix should take. Nothing measured so far requires it.

Two findings from T11 are untouched here and remain open as scoped tasks: the rate-limiter deadlock in the database cache store (T16) and the receipt worker's memory ceiling (T17). mPDF logged PHP's 128 MiB exhaustion again during both drains, exactly as T11 recorded.
