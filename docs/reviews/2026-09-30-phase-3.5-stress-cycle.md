# Phase 3.5 pre-production stress cycle — 2026-09-29–30

This is a repeat of the [T11 load harness](../../tests/Load/README.md) against
the [T12 development-harness targets](../superpowers/specs/2026-07-20-training-center-dashboard-design.md#11-operations).
It is not a production service-level claim: the hosting provider and production
web stack remain undecided and unmeasured.

## Target and method

- Code under test: `548b4c3` (the T12 merge on `main`), checked out in the
  isolated `docker/dev-linux` workspace. Docker Desktop 29.8.0 on WSL2 Linux
  x86-64, 16 available vCPUs and 7.61 GiB available memory. App PHP 8.4.25
  with the built-in server and `PHP_CLI_SERVER_WORKERS=8`; MySQL 8.4.7;
  Redis 8.4.0; pinned `grafana/k6:1.4.0` on the same Docker network.
- Actual selected drivers: queue `redis` (Horizon running), cache
  `database`, sessions `database` with 480-minute lifetime. Horizon's local
  supervisor reported three workers on `redis:default`. The target was
  started from its existing stopped containers, not recreated.
- The allowlisted, disposable `training_center_performance` database was
  rebuilt with the medium profile: 4,000 students, enrolments and charges, and
  8,000 payments and allocations. This models a medium-sized single centre,
  not a claim that the future deployment will have this workload. The seeded
  owner completed normal panel password rotation; 20 independent sessions
  were minted, and login was excluded from measured flows because Filament
  throttles it.
- Each k6 script uses 20 VUs for five minutes. Search and reports read the
  untouched fixture; enrol-and-collect quick-creates and writes real payment
  rows; receipt download uses completed PDFs. The scripts check rendered data,
  not only HTTP status. Throughput is successful flows / 300 seconds. The
  receipt script's 25-second per-VU pause keeps it within the 60/minute/user
  limiter; that throughput is deliberately limiter-shaped.

## Evidence and follow-up

The request-latency misses are measurements, not root-cause diagnoses. During
search the app container was observed at 579.88% CPU and MySQL at 122.94% in
one `docker stats --no-stream` sample; during reports, 670.99% and 190.45%.
Those point to substantial concurrent work but do not distinguish PHP
development-server queueing, database work, and Livewire rendering. The
search p95 rose from T11's 544 ms to 1,010 ms (48.5% over T12's 680 ms target)
and reports from 3,024 ms to 3,910 ms (3.4% over 3,780 ms).

While the first collection was writing, `queue:monitor redis:default`
reported 1,076 pending receipt jobs with an oldest wait of two minutes, then
1,678 pending with an oldest wait of four minutes shortly after the request
run ended. It eventually drained to zero; all 2,251 new payments acquired
receipt paths and verified existing files, and `failed_jobs` remained zero.
The second collection rerun again left 1,854 pending jobs with an oldest wait
of seven minutes while only 794 of 2,654 PDFs had been attached. The last
nonzero monitor snapshot was 234 pending at 22:54:53 UTC; the first zero
snapshot was 22:59:53 UTC, roughly 25–30 minutes after collection ended.
Horizon reported three local workers. The queue is asynchronous: the
collection request result does not prove receipt readiness. Queue wait has no
T12 objective, explicitly deferred until it is measured under load. This
sample is evidence of a backlog, not a per-job latency distribution or a
production breach.

The following are **proposed, separately scoped follow-ups**, not changes
made by T13. They require owner scheduling and cross-review before code work:

1. **Search latency attribution (measurement only).** Reproduce the 20-VU
   search miss on a clean medium fixture; separate page GET from Livewire
   update timing in k6, and inspect SQL plans, rendered payload size and
   server utilisation read-only. Do not infer an index fix from CPU alone.
   Proposed edit scope: `tests/Load/k6/student-search.js` and
   `docs/reviews/2026-09-30-p35-t13-search-latency-investigation.md`.
   A later application fix needs its own measured, approved file scope.
2. **Report latency attribution (measurement only).** Measure each of the
   four report variants separately, including GET versus Livewire update,
   and inspect the slow variant's query plan read-only before naming a fix.
   Proposed edit scope: `tests/Load/k6/reports.js` and
   `docs/reviews/2026-09-30-p35-t13-report-latency-investigation.md`.
   No report class is pre-authorised for editing by this proposal.
3. **Receipt queue-drain profile (measurement only).** Repeat the medium
   collection/drain on the same three-worker topology with timed queue-depth
   samples, PDF-ready counts and worker-failure counts. State the observed
   total drain window and whether enqueue-to-start and enqueue-to-ready
   distributions are actually observable; if not, scope instrumentation
   separately before proposing a queue-delay objective. Proposed edit scope:
   `docs/reviews/2026-09-30-p35-t13-queue-drain-profile.md` and
   `tests/Load/README.md` for the repeatable measurement procedure.
   `config/horizon.php`, receipt jobs and system-design §11 are **not**
   pre-authorised for editing; coordinate with the existing T17 task first.

The known T16 database-cache rate-limiter deadlock and T17 mPDF memory
exhaustion already have their own scopes in the phase plan; this report does
not duplicate or fix them. This run saw **zero** receipt-download errors
in 240 attempts, so it did not reproduce T16; one clean sample cannot prove
that intermittent deadlock is gone. During the second receipt drain the
application log again recorded PHP's 128 MiB memory exhaustion in mPDF
`TTFontFile.php:4707`, including at 22:56:49–22:57:52 UTC. All PDFs
ultimately arrived, so T17 remains a capacity/retry finding rather than
observed missing documents.

## Limits and cleanup

These figures use PHP's development server in a local container, not nginx
or a chosen VPS. The 20-VU scenario is repeatable and deliberately heavier
than a quiet centre desk, but does not model a verified production arrival
distribution. The search run slowed sharply near its last minute; there is
no per-request trace to explain that tail. T12's request-flow targets are
regression detectors for this harness, and its absent queue-delay target
remains absent here.

Both signed 20-session manifests were revoked with the guarded
`load:revoke-sessions` command (exit 0), each before its fixture was left
behind. Receipt jobs and `failed_jobs` were zero after the second drain.
The final `composer verify` gate is reported in the pull request. No
application code was changed by this task.
