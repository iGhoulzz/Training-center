## What four review rounds found, and the rule that follows

The same author error, five times: **a change was scoped against a documented
invariant without reading the file that documents it.**

- Round 1 — §4's "Sessions: database-backed", and `StudentPaymentHistory`'s "no
  period filter".
- Round 2 — `WageCostReport`, whose opening docblock is headed *"THE TRAP THIS
  CLASS EXISTS TO AVOID"* and warns against exactly the change round 2
  instructed; and `Reference`'s audit-log warning, eight lines below the
  placeholder text round 2 did read.
- Round 2 also produced a **confidently wrong inventory**: two of T03's twelve
  classifications were wrong in opposite directions — one already-bounded site
  marked broken, one unbounded site marked safe.
- Round 3 bounded a UI result without bounding its upstream query, replaced a
  range scan with a query-per-month loop, and left credential-minting and Linux
  target prerequisites as implementation details. Round 4 makes the source
  query, constant query count, pre-insert clock, destructive-data guard and
  infrastructure dependencies part of the contracts themselves.

**The rule, for this plan and the phase-4 plan after it:** before a task's scope
is written, the full docblock of every file it touches is read, and every
classification row carries the evidence that justifies it rather than a verdict.
A wrong inventory is more dangerous than a deferred one, because the next reader
does not re-check it.

Both owner decisions are resolved for this plan's purposes: there is no launch
date but readiness is required (Wave 6), and the expenses question no longer
gates anything here because the reports rework moved to the design phase.

**Goal:** Close the gap between what the system does and what it was designed to
do, and act on the owner's first review of the running application — before

### Task 1 — Queue on Redis, and the session lifetime drift
**Owner: Codex · `p35/t01-redis-defaults` · depends on nothing**

**File scope**
- `.env.example`
- `docs/superpowers/specs/2026-07-20-training-center-dashboard-design.md` — §11 only
- `tests/Feature/Tooling/ProductionDefaultsTest.php` — **new**
- **Joins:** `.env.example` with T10b; system design §11 with T10a, T10b
  and T12.

**Does**

**Round 1 got this wrong and the correction is the task.** Round 1 changed
`SESSION_DRIVER` to Redis and called it drift-closing. System design **§4 line 89
says "Sessions: database-backed, 8-hour idle timeout"** — an authoritative
decision this task does not own. §11 assigns **only the queue** to Redis. Redis
cache was never in either document.

So the scope is now three separate things, correctly labelled:

1. **`QUEUE_CONNECTION=redis`** — the genuine design requirement, §11.
2. **`SESSION_LIFETIME=120` → `480`** — **the real drift, which round 1 walked
   past while inventing a different one.** §4 promises an eight-hour idle
   timeout; the shipped example gives two hours. Sessions stay
   `SESSION_DRIVER=database`.
3. **Cache stays `database`.** Redis cache is a new operational choice, not a
   documented requirement, and this plan will not smuggle one in as drift. If it
   is wanted it needs its own owner decision.

**Redis is not present in this development environment** — no `phpredis`
extension, no `predis` in `composer.json`, nothing listening on 6379, while
`.env.example` already names `REDIS_CLIENT=phpredis`. The production VPS gets
Redis from Ploi. So the example file must make the fallback explicit rather than
handing a fresh clone a default that cannot connect.

**Done when**

`.env.example` sets the queue to Redis and states the database fallback in the
same file · `SESSION_LIFETIME` is 480 and sessions remain database-backed · the
cache driver is unchanged and that is stated as deliberate · a test asserts the
example file's drivers and lifetime, so the next drift fails a run rather than
reaching a deployment · §11 records which driver production uses and what happens
without Redis · the local `.env` is untouched · `composer verify` green.

### Task 2 — The super-admin role-id lookup
**Owner: Claude · `p35/t02-superadmin-role-id` · depends on nothing**

**File scope**
- `app/Domain/Staff/Support/SuperAdminRoleId.php` — **new**; the resolver
- `app/Models/Role.php` — `superAdminId()` delegates to it
- `app/Providers/AppServiceProvider.php` — **seam**; `$this->app->scoped(SuperAdminRoleId::class)`
- `tests/Feature/Staff/UserResourceQueryCountTest.php` — **new**
- `tests/Feature/Staff/SuperAdminRoleIdLifecycleTest.php` — **new**
- **Joins:** `AppServiceProvider` with T04 and T10a.

**Does**

`Role::superAdminId()` runs a fresh `SELECT` on `name` + `guard_name` every call.
It is called from `User::isSuperAdmin()`, which the User policy calls per row for
row-action visibility. The audit measured 28 of these on a 10-row page, half of
the 56 repeated rank statements.

**Never cache the User pivot result.** `User::isSuperAdmin()`'s own docblock
records why the fresh id-based lookup exists: a stale in-memory roles relation
once let the last super admin be deleted. The Actions must stay
self-authorizing against current database state. Only the *role id* is memoized,
and the role id is not the authorization read.

**Cache lifetime is a requirement, not an assumption** — this is P3-T15's
re-review point and it is the hard part of this task. Prove the memo cannot leak
across HTTP requests, queue jobs, or long-lived workers, and account for
bootstrap and seeding paths, where the canonical role is created.

**The mechanism is `$this->app->scoped()`, named here rather than chosen on the
branch.** A `static` property on `Role` survives between jobs in a long-lived
queue worker — the exact leak this task exists to prevent. Laravel rebuilds
`scoped` bindings per request **and** between queued jobs, which is the lifecycle
the obligation requires. `Role::superAdminId()` delegates to the resolver so no
caller changes, and **it is a scoped binding, not a singleton** — round 2 called
it a singleton, which is the binding that would leak.

**Done when**

`UserResourceQueryCountTest` drives the real `ListUsers` component and pins the
statement count · the count falls by the role-id lookups and the pivot `exists()`
reads remain uncached · **mutation-proved both ways**: removing the binding
regresses the count, and changing a user's roles before an Action still causes the
Action to authorize against current state · `SuperAdminRoleIdLifecycleTest` proves
**a same-worker two-job case** does not reuse the first job's value, and **a
missing-role-then-seeded case** does not cache a null into a permanent false ·
`composer verify` green.

**Report filter implementation:** convert `ReportPage`'s handwritten filter
descriptors to a Filament `Schema` rendered by the existing Blade view. The
`student_id` field is a remote-searchable `Select` with
`getSearchResultsUsing()` and `getOptionLabelUsing()`; the date and month inputs
remain schema fields bound to the same `filters` state path, and the form still
submits to `applyFilters()`.

**The instructor-assignment picker is the exception to a mechanical Select
rewrite, and its replacement is decided here.** Filament 5's `CheckboxList`
implements client-side search over a fully materialized options array; it has no
`getSearchResultsUsing()` callback. Replace it with a searchable
`Select::multiple()` using both `getSearchResultsUsing()` and
`getOptionLabelsUsing()`. Preserve the submitted `list<int>` shape consumed by
payroll creation and let the existing Action re-authorize every selected id.

The remote search must also be bounded at its source. Filtering
`PayrollCalculator::availableInstructorAssignments()` after it returns is not a
fix: that method currently plucks every paid id and asks
`EnrollmentQueryService::allInstructorAssignments()` to hydrate the entire
centre. Add these exact published interfaces:

```php
EnrollmentQueryService::searchInstructorAssignments(
    Builder $excludedAssignmentIds,
    string $search,
    int $limit,
): Collection

EnrollmentQueryService::instructorAssignmentsById(array $ids): Collection

PayrollCalculator::searchAvailableInstructorAssignments(
    string $search,
    int $limit = 25,
): Collection
```

`PayrollCalculator` supplies a Finance-owned subquery selecting finalized
non-null `payroll_lines.batch_instructor_id`; Enrollment composes it as `whereNotIn`
without learning Finance's table schema, joins only the label sources, and
applies `limit(25)` before `get()`. The by-id method is bounded by the selected
ids and exists only to redisplay the multiple Select's current values. Both
return `Collection<int, array{id: int, batch_id: int, batch_code: string,
user_id: int, user_name: string, assigned_hours: int}>`, never Enrollment
models, preserving the existing domain boundary. Search matches user name or

`MonthRange` is a value object over `(fromYear, fromMonth, toYear, toMonth)`.

boundary to the other:

```php
MonthRange::between(int $fromYear, int $fromMonth, int $toYear, int $toMonth): self
MonthRange::single(int $year, int $month): self

WageCostReport::totalForMonths(MonthRange $range): Money

/** @return array{revenue: Money, wageCost: Money, profit: Money} */
ProfitReport::forMonths(MonthRange $range): array
```

Those exact return shapes preserve the existing one-month contracts while
aggregating the whole selected range.

selected range, not a month-by-month series. The design handoff asks its

series. If a later design does, that is a separate `byMonth(MonthRange)`-style
interface and test contract rather than a silent change to `forMonths()`.

revenue half and combines it with the set-based wage total. The query count is
therefore constant: two for wage cost and three for Profit, whether the range is
one month or 120.

caller breaks and the two halves still align from one local-month value.

**THE PLACEHOLDER MECHANISM IS ABANDONED, AND ROUND 2'S REVIEW IS WHY.** Round 2
told this task to copy `Reference`'s placeholder-in-transaction. Two measured
facts make that unusable here:

- `PLACEHOLDER-` plus a UUID is **48 characters**. `students.student_code` is

- `student_code` is in `Student::auditedAttributes()` and `code` is in

| | Format | Fits |
|---|---|---|
| Student | `STU-{year}-{6}` | 15 chars in `varchar(30)` |
| Batch | `BAT-{year}-{6}` | 15 chars in `varchar(40)` |

generated `created_at`. `CertificateReference` already records the New-Year trap:

clock reads. The Action captures one UTC `CarbonImmutable` before its retry loop,

`created_at` and `updated_at` on every attempt. `IdentifierCode` derives the

```php
IdentifierCode::student(DateTimeInterface $createdAt): string

CreateWithIdentifierCodeAction::createStudent(User $actor, array $attributes): Student
CreateWithIdentifierCodeAction::createBatch(User $actor, array $attributes): Batch
```

build of them to install; Horizon supervises workers by forking and signalling
them. `phpredis` is likewise absent, so Windows PHP cannot speak to a Redis
server even when one is running in a container. A Redis container alone therefore
does **not** unblock anything: what is missing is PHP running on Linux.

**The starting point is better than it looks.** WSL 2 is already enabled on the
development machine — `wsl --status` reports default version 2 with Docker
Desktop's distro registered — so this is adding a distribution, not enabling a
platform.

**What the environment must provide**, stated as capabilities so a container or a
spare Linux host satisfies it equally:

- PHP 8.4 with `pcntl`, `posix` and `redis` loaded;
- Composer, and a `composer install` that completes with Horizon's platform
  requirements satisfied;
- a running Redis server the application can reach;
- **a test database of its own, NOT the Windows one.** This is the reverse of
  what the first draft of this task required, and the reverse is dangerous.

  `tests/bootstrap.php` serialises suites with a file lock, and **that lock does
  not cross the OS boundary — twice over.** `SerialLock::pathFor()` builds its
  path from `sys_get_temp_dir()`, which is `%TEMP%` on Windows and `/tmp` on
  Linux. And `Repo::lockKey()` hashes the canonicalised
  `git rev-parse --git-common-dir`, which is `C:/Users/.../.git` from Windows and
  `/mnt/c/Users/.../.git` from WSL. Different directory, different hash: two
  processes, two locks, no contention.

  So pointing the Linux environment at `training_center_test` would let a Windows
  suite and a Linux suite run `migrate:fresh` against one schema simultaneously,
  with nothing to stop them. The failures would surface as rows vanishing
  mid-test and read as flakiness for as long as it took someone to suspect the
  cause. A separate database is what isolates them; the shared one is only safe
  because a lock currently covers every process that touches it, and a Linux
  process is not one of those.

  The runbook names the database and the `DB_DATABASE` value that selects it.

### Task 15 — The payment-allocation deadlock T11 measured
**Owner: Claude · `p35/t15-allocation-deadlock-fix` · depends on T11 · blocks T12**
— the branch carries a suffix because `p35/t15-allocation-deadlock` held the plan

**File scope**
- `app/Domain/Finance/Support/ChargeBalance.php`, `app/Domain/Finance/Services/PaymentInvariantService.php`, `app/Domain/Finance/Actions/RecordPaymentAction.php` — **whichever of the three the reproduction actually implicates; touching all three without evidence is not in scope**

- `docs/reviews/2026-09-28-phase-3.5-load-baseline.md` — a closing note recording the rerun, not a rewrite of the measurement
- `docs/superpowers/plans/2026-09-07-phase-3.5-hardening-and-feedback.md` — this task's entry, T12's owner line, the seam rows naming T15, and the wave summary. The deferred row this came from was removed when the task was scoped, so there is none left to edit
- **Possible, and to be raised before it is used:** a migration, if the evidence says the index is what has to change
- **Joins:** `ChargeBalance` with nothing open; T12 waits on this task's rerun

**Does**

**This is the money path failing under ordinary concurrency, not a load-test artefact.** T11 measured **51 HTTP 500s in 2,821 enrol-and-collect flows — 1.80%** — every one a MySQL 1213 deadlock while inserting into `payment_allocations` from `RecordPaymentAction`. At twenty concurrent sessions, roughly one collection in fifty-five failed.

**What was measured is HTTP flows**, not tills: no operator handed over money in that run. The reason this ranks above the other two findings is the risk that shape carries in the real thing — on that endpoint, in use, cash has typically changed hands before the request is sent, so a 500 leaves a person holding money the system has no record of.

**The mechanism, confirmed on 2026-09-28 before this plan merged.** It was written below as a hypothesis; the reproduction and InnoDB's own deadlock report have since confirmed it, and narrowed it. Two tills on **different** bills deadlock in **11 of 12 rounds** on Windows and **6 of 6** in the Linux target, always on the `payment_allocations` insert. Highly repeatable, not per-round certain: the committed test therefore needs enough rounds that a pass before the fix is not luck, and that threshold is part of the fix, not an afterthought. `SHOW ENGINE INNODB STATUS` says why:

```
*** (1) HOLDS THE LOCK(S):
RECORD LOCKS ... index payment_allocations_charge_id_index ... lock_mode X
 0: len 8; hex 73757072656d756d; asc supremum;;
*** (1) WAITING FOR THIS LOCK TO BE GRANTED:
RECORD LOCKS ... index payment_allocations_charge_id_index ... lock_mode X insert intention waiting
```

— mirrored exactly by transaction (2), for charges 11 and 12.

**The narrowing matters.** Both transactions hold an X lock on the index's **supremum** record, which is the gap after the last entry, and both then need an insert-intention lock on it. A `FOR UPDATE` equality scan takes that gap lock when it matches **no rows** — that is, on a charge with no allocations yet. Enrol-and-collect creates a new bill on every flow, so every flow locks the same supremum gap, which is why T11 saw this in the write flow and nowhere else. Any fix has to address the empty-range case specifically; making the scan cheaper or better-indexed would not touch it.

**The hypothesis as originally written**, kept because the entry should show what was reasoned before it was measured: `ChargeBalance::allocatedForUpdate()` runs

```sql
SELECT COALESCE(SUM(payment_allocations.amount), 0)
FROM payment_allocations
INNER JOIN payments ON payments.id = payment_allocations.payment_id
WHERE payment_allocations.charge_id = ? AND payments.reversed_at IS NULL
FOR UPDATE
```

Under REPEATABLE READ a `FOR UPDATE` range scan takes next-key locks — the matching index entries **and the gaps around them** — on `payment_allocations.charge_id`, and on the joined `payments` rows. Every concurrent collection also inserts into that same index, which needs an insert-intention lock in a gap. Two tills working on **different** bills can therefore each hold a gap the other needs. That matches the observed shape: the charge row lock already serialises two tills on one bill, so a deadlock at this rate must be coming from transactions that never touch the same charge.

**Why the evidence had to come from the Linux target.** The dev MySQL account cannot read `performance_schema.data_locks` or `SHOW ENGINE INNODB STATUS` — it lacks `PROCESS`, which `ChargeBalance` itself notes as the reason an earlier claim there was deliberately left unverified. The target's root account can, so the report above was taken in `docker/dev-linux`, not reasoned about from Windows.

**What the fix may not do.** Store the allocated total on the charge — non-negotiable 2 forbids derived financial values. Drop the locking read for a plain one — a snapshot read is exactly the staleness `outstandingForUpdate()` exists to defeat, and REPEATABLE READ would hand back a figure taken before the charge lock was granted. Retrying blindly is also not a fix on its own: a retry that re-runs a partially applied transaction has to be safe **because** the insert-first idempotency key makes it so, and that argument belongs in the code where someone will read it.

**Done when**

The reproduction above is committed as a test that **fails before the change for the right reason** — a 1213 on the allocation insert, not a timeout or an assertion about timing — and the harness it borrows from `PaymentConcurrencyTest` is reused rather than re-invented · the lock sets are already read and recorded above, so what remains is to keep them true · the fix is the smallest one the evidence supports, and its safety argument is in the code · T11's enrol-and-collect flow is rerun on the same fixture and profile, and the deadlock 500s are **zero**, with the new figure recorded beside the original rather than replacing it · `composer verify` green.

**Outcome, 2026-09-29**

The fix is a bounded retry of the collection transaction, in `RecordPaymentAction` and nowhere else. `ChargeBalance` and `PaymentInvariantService` were read and left alone: the gap lock is theirs, but nothing they could give up would remove it without giving up the locking read, which is the staleness defence above.

**The rerun met the zero, and the first bound was refuted on the way.** Three attempts came from arithmetic and was wrong — one flow in 2,657 still failed with the same 1213, which is a 1-in-70 event if the attempts were independent, so they are not: Laravel retries immediately and a loser restarts into the same gap. At five attempts the rerun recorded **0 errors in 2,764 flows**, with throughput back at baseline. Both runs are in the report's closing note, because the refuted number is the reason the accepted one is trustworthy.

**No residual rate is claimed, and the report says why.** One failure cannot size a conditional probability; a zero count cannot distinguish rare from never. What the clean run supports is an upper bound of roughly 0.11% by the rule of three — an established improvement of better than twelvefold on T11's 1.80%, with the true size unmeasured.

**One thing this task did not settle, and it is the owner's.** Retrying makes the failure rare, not unreachable — InnoDB was still deadlocking on the supremum gap eighteen seconds before the clean run ended. The only construction that removes the conflict outright is running the collection transaction under READ COMMITTED, which takes no gap locks. That is a change to the isolation level of the money path; nothing measured requires it, and **T12's error-rate target is the right place to weigh it**, since that is the task this one was blocking. T12 inherits a bound, not a rate: the post-fix failure rate is known only to be below roughly 0.11%, so an objective tighter than that needs evidence this task did not produce.

**Does**

T11 measured **two HTTP 500s in 240 receipt downloads (0.83%)**, and they were not 429s: both were MySQL 1213 deadlocks inside `Illuminate\Cache\RateLimiter`, writing to the **database** cache store. `routes/web.php:50` puts `throttle:60,1` on the receipt-download route — line 42 is the staff-certificate route, which is a different throttle — so every download increments one counter row, and T11's twenty sessions all belonged to one user.

**The decision this may reach, and why it is the owner's.** The obvious fix — put the limiter's cache on Redis, which production already runs for queues — is exactly what system design §11 refuses by default: "moving either to Redis is a separate operational decision, not implied by the queue requirement". **Done when**

The deadlock is reproduced by a test that fails first for the right reason — **amended by the owner on 2026-10-08, because the fix is configuration rather than code.** A configuration change can only regress through configuration, so what is committed is a guard on the shipped configuration, watched failing three ways: with no limiter key, with `database`, and with `file`. **Outcome, 2026-10-07**

**The mechanism is not the one this entry assumed, and the lock sets settled it.** No gap lock is involved: both transactions take a **shared** record lock during an `INSERT IGNORE` duplicate-key check and then each needs an **exclusive** one on that same record, which is delete-marked by the expiry DELETE that `DatabaseStore::many()` issues during a **read**. Every side reads `locks rec but not gap`, so unlike T15 a READ COMMITTED transaction would not help. Reproduced at 63 deadlocks in 182,327 attempts in the container.

**The fix needed no change to the cache decision**, which is the branch this entry hoped for. Laravel binds the limiter to its own `cache.limiter` store; that key did not exist, so the limiter inherited `cache.default`. It is now `redis` while the application cache and sessions stay database-backed, so §11's standing refusal is narrowed and recorded rather than reopened. The owner took that decision on 2026-10-06.

**`file` was rejected on correctness**: `FileStore::increment()` is an unlocked read-modify-write, so concurrent hits lose increments and the throttle admits more than it states.

**The approved concurrency-test expansion went unused.** `ReceiptDownloadConcurrencyTest.php` was approved on 2026-10-06 when the fix was expected to need a subprocess race. Because the fix turned out to be configuration, the committed guard is a configuration assertion and fits `ReceiptDownloadTest.php` as this entry originally said — so the expansion is recorded as granted and not taken, rather than spent for its own sake.

**The guard asserts the shipped configuration, not the test process's.** `phpunit.xml` pins `CACHE_STORE=array`, and with no limiter key the limiter inherited it — which is why no test ever caught this. Asserting `config('cache.limiter')` alone would read the pin and pass whether or not the fix exists.

**Owner: Claude · `p35/t17-receipt-worker-memory` · depends on T11**

- `tests/Feature/Finance/ReceiptGenerationTest.php` — where the measured peak is pinned

- `docs/superpowers/plans/2026-09-07-phase-3.5-hardening-and-feedback.md` — this task's entry and the lines that name it
- `docs/superpowers/specs/2026-07-20-training-center-dashboard-design.md` — **§11 only, and only if the worker ceiling changes**
- **Joins:** §11 with T01, T10a, T10b, T12 and T16 — see the seam table

**Does**

During T11's receipt drain, **mPDF exhausted PHP's 128 MiB limit**. Every one of the 2,770 successful payments eventually got its PDF, so this is headroom rather than data loss. It was logged rather than silent: T11 found it in the application log, and the drain completed. A job that dies on memory and is retried into success is a cost and a warning, not an outage.

**Two different 128s, and the task starts by telling them apart.** `config/horizon.php` sets a supervisor `memory` of 128, which is the ceiling at which Horizon *restarts* a worker; PHP's own `memory_limit` is what actually threw. Raising the wrong one changes nothing and looks like a fix. The first output of this task is which limit was hit, and what one receipt render actually costs at the medium fixture.

**Done when**

The peak memory of a single receipt render is measured, not estimated · which of the two limits threw is stated with its evidence · the change is the smallest one that measurement supports, and if it is a limit rather than the render, the number is justified by the measured peak plus stated headroom · the drain is repeated under the same load with no exhaustion logged · `composer verify` green.

**Outcome, 2026-10-06**

**The either/or above was wrong, and the measurement is what showed it.** PHP's `memory_limit` threw — `Allowed memory size of 134217728 bytes exhausted` is PHP's own fatal and 134,217,728 is exactly 128 MiB — **but it threw because the supervisor ceiling was also 128 and so could never fire first.** Laravel checks that ceiling only after a job returns (`Worker::runJob()` at `Worker.php:267`, then `stopIfNecessary()` at `:287`), so an equal pair requires a worker to *finish* a job while already holding PHP's whole limit. The recycle was unreachable by construction. "Raising the wrong one changes nothing" was right about raising; it did not anticipate that *lowering* the other one is the fix.

**What one render costs.** Twenty-five renders back to back in one process, `memory_limit=-1` so the curve was not truncated by the limit under investigation: the process starts near 42 MiB, the first render adds **22 MiB** as mPDF loads and subsets its fonts, and every render after that adds about **2 MiB that is never released** — 114 MiB at render 25, still linear. Exhaustion arrives near render 32, which over a 2,770-receipt drain on three workers is roughly thirty deaths each. **The growth is accumulation, not one expensive render**, so the recycle is what keeps a drain alive. The process peak equalled the allocation after every sampled render, which bounds a single render's transient demand at the 22 MiB cold start rather than leaving it inferred from retained memory.

**The change is `config/horizon.php` alone**: the ceiling drops 128 → **96**, leaving 32 MiB beneath PHP's default, which is more than the dearest single render observed. **Either side of the pair could have moved** — review corrected an earlier claim here that raising PHP's limit would merely postpone the death; with PHP above the ceiling a job finishes and the post-job check recycles, so that is a real alternative. Lowering was chosen because this repository configures Horizon but not the production `php.ini`, and because a recycled worker holds flat memory where a higher limit multiplies resident memory by the ten production processes. `docker/dev-linux/Dockerfile` and `docs/LINUX-DEV-TARGET.md` stay untouched, because the PHP limit does not have to change. `GenerateReceiptJob` stays untouched, because the render is not the defect. §11 records the invariant — the ceiling must sit below the limit the workers run under — since that is what a deployment raising `memory_limit` has to keep true. `ReceiptGenerationTest` asserts the property rather than the number, and was watched failing with the ceiling restored to 128.

**Scope approved 2026-10-06.** The owner accepted lowering the Horizon ceiling even though PHP's limit is what threw, and stated that approving the scope does not waive the test below.

**The drain repeat is done, 2026-10-06, and the entry is discharged.** Same target, same rebuilt medium fixture, same profile: **2,358 collection flows with 0 errors, all 2,358 receipts rendered and attached, `failed_jobs` 0, and not one `Allowed memory size` entry** — the container's count stood at 410 before and after, accumulated from T11's and T13's drains. The queue kept pace rather than backing up.

The Linux per-render figures are in the report beside the Windows ones. They confirm the container runs at PHP's stock `memory_limit=128M`, confirm the ~2 MiB accumulation, and correct two things: the cold start is 16.0 MiB rather than 22.0, and a render's transient **can** exceed its end state by one 2 MiB chunk, so the Windows claim that peak always equalled the final allocation is withdrawn. A warm render demands 4.0 MiB above where it begins, which is what makes 96 defensible — a worker recycled at the ceiling finishes at about 100 MiB, well inside 128.

Two limits on the evidence are recorded rather than smoothed over: this run was somewhat lighter than T11's and T13's, and the plateau at 120.5 MiB was measured render-only, where the real job also holds the bytes and writes them.
