# Phase 3.5 — Hardening and Owner Feedback Implementation Plan

**Status: DRAFT, round 2 — six P1 blockers from round 1 corrected. No task may begin until this merges green.**

Both owner decisions are resolved for this plan's purposes: there is no launch
date but readiness is required (Wave 6), and the expenses question no longer
gates anything here because the reports rework moved to the design phase.

**Goal:** Close the gap between what the system does and what it was designed to
do, and act on the owner's first review of the running application — before
phase 4 adds the public site and the Arabic pass on top.

**Why this is not phase 4.** System design §2 already defines phase 4 as "Public
site and Arabic — landing pages, course listings, contact, and the full
bilingual pass", and §13 records a limitation phase 4 must close. The work here
is different in kind: it is hardening, drift-closing and owner feedback, and

work behind a bilingual pass.

**Where the work came from.** Three sources, and they are kept distinguishable
because they carry different evidence:

- **P3-T15's performance audit** (`docs/reviews/2026-09-06-performance-audit.md`),
  which measured two Medium findings and deliberately deferred implementation.
- **The owner's review of the running application**, gathered 2026-09-06/07.
  Some of it contradicts assumptions that were never put to the owner.
- **Drift found while investigating those**, most of it doc-versus-code.

## Two owner decisions gate part of this plan

**Neither is mine to make, and two tasks below cannot be scoped until they are
answered.**

### Decision 1 — expense tracking

System design **§12 explicitly lists "Expense tracking beyond staff wages" as out
of scope.** The owner has asked for rent and similar costs to be recorded and to
reach the Profit report.

The owner may change the scope — it is their system. But CLAUDE.md requires §12
to be checked before adding anything not asked for, so this needs a deliberate
spec amendment rather than a task that quietly overrides it.

If approved, it is a domain area rather than a screen: a table, a category
concept, a write Action, permissions, and a change to what "Profit" computes.

**No task in this plan is blocked on it**, and that is deliberate. The reports UI
rework has moved to the owner's planned design phase, so nothing here is waiting
on the answer. What the answer does affect is **that** phase: a design for a
Profit page cannot be drawn without knowing whether overheads exist, so this
decision wants settling before the design phase begins rather than before this
plan does.

Also open if approved: is the category a free-text reason, a fixed enum, or a
managed lookup table? It changes the schema, and it changes what a designer has
to lay out.

### Decision 2 — launch date: ANSWERED

**There is no target date, and readiness is still required.** The owner's words:
"there is no deploy launch date but we need to be ready."

That is not the same as "later". It means the readiness work is real work with no
deadline attached, so it belongs in Wave 6 below rather than in a checklist that
nobody owns. What it removes is the sequencing pressure: nothing here has to be
rushed to hit a date, and a readiness task that finds a problem is allowed to
take the time to fix it.

One item genuinely cannot become a task — see Wave 6 — because it is hosting-panel
configuration rather than anything that can be reviewed as a diff.

## Wave 1

### Task 1 — Redis as the production default
**Owner: Codex · `p35/t01-redis-defaults` · depends on nothing**

**File scope**
- `.env.example`
- `docs/superpowers/specs/2026-07-20-training-center-dashboard-design.md` — §11 only
- `tests/Feature/Tooling/ProductionDefaultsTest.php` — **new**
- **Joins no seam.**

**Does**

**Round 1 got this wrong and the correction is the task.** Round 1 changed
`SESSION_DRIVER` to Redis and called it drift-closing. System design **§4 line 89
says "Sessions: database-backed, 8-hour idle timeout"** — an authoritative
decision this task does not own. §11 assigns **only the queue** to Redis. Redis
cache was never in either document.

So the scope is now three separate things, correctly labelled:

1. **`QUEUE_CONNECTION=redis`** — the genuine design requirement, §11.
2. **`SESSION_LIFETIME=120` → `480`** — **the real drift, which round 1 walked
   past while inventing a different one.** §4 promises an eight-hour idle
   timeout; the shipped example gives two hours. Sessions stay
   `SESSION_DRIVER=database`.
3. **Cache stays `database`.** Redis cache is a new operational choice, not a
   documented requirement, and this plan will not smuggle one in as drift. If it
   is wanted it needs its own owner decision.

**Redis is not present in this development environment** — no `phpredis`
extension, no `predis` in `composer.json`, nothing listening on 6379, while
`.env.example` already names `REDIS_CLIENT=phpredis`. The production VPS gets
Redis from Ploi. So the example file must make the fallback explicit rather than
handing a fresh clone a default that cannot connect.

**Done when**

`.env.example` sets the queue to Redis and states the database fallback in the
same file · `SESSION_LIFETIME` is 480 and sessions remain database-backed · the
cache driver is unchanged and that is stated as deliberate · a test asserts the
example file's drivers and lifetime, so the next drift fails a run rather than
reaching a deployment · §11 records which driver production uses and what happens
without Redis · the local `.env` is untouched · `composer verify` green.

### Task 2 — The super-admin role-id lookup
**Owner: Claude · `p35/t02-superadmin-role-id` · depends on nothing**

**File scope**
- `app/Models/Role.php` — **seam**; sole writer
- `tests/Feature/Staff/UserResourceQueryCountTest.php` — **new**
- **Joins no seam.**

**Does**

`Role::superAdminId()` runs a fresh `SELECT` on `name` + `guard_name` every call.
It is called from `User::isSuperAdmin()`, which the User policy calls per row for
row-action visibility. The audit measured 28 of these on a 10-row page, half of
the 56 repeated rank statements.

**Never cache the User pivot result.** `User::isSuperAdmin()`'s own docblock
records why the fresh id-based lookup exists: a stale in-memory roles relation
once let the last super admin be deleted. The Actions must stay
self-authorizing against current database state. Only the *role id* is memoized,
and the role id is not the authorization read.

**Cache lifetime is a requirement, not an assumption** — this is P3-T15's
re-review point and it is the hard part of this task. Prove the memo cannot leak
across HTTP requests, queue jobs, or long-lived workers, and account for
bootstrap and seeding paths, where the canonical role is created.

**Done when**

**The mechanism is named here, not chosen at implementation time.** A bare
`static` property on `Role` survives between jobs in a long-lived queue worker,
which is exactly the leak this task exists to prevent. Use a **container-scoped
resolver** — a singleton the framework rebuilds per request and per queued job —
rather than static state. If a provider registration is required, it is declared
scope before the branch is cut, and it collides with T04's `AppServiceProvider`
seam, so the two are placed in different waves.

**Done when**

A query-count test drives the real `ListUsers` component and pins the statement
count for a populated page · the count falls by the role-id lookups and the pivot
`exists()` reads remain uncached · **mutation-proved both ways**: removing the
memo regresses the count, and changing a user's roles before an Action still
causes the Action to authorize against current state · **a same-worker two-job
test** proves the memo does not survive from one queued job into the next · **a
missing-role-then-seeded test** proves a null result is not cached into a
permanent false · `composer verify` green.

### Task 4 — Non-production lazy-loading guard
**Owner: Claude · `p35/t04-lazy-loading-guard` · depends on nothing**

**File scope**
- `app/Providers/AppServiceProvider.php` — **seam**; sole writer
- `tests/Feature/Tooling/LazyLoadingGuardTest.php` — **new**
- **Joins:** `AppServiceProvider`.

**Does**

`Model::preventLazyLoading(! $this->app->isProduction())`, enabled for local and
testing and left off in production initially. An unexpected lazy load should fail
in development and CI, not turn a public request into a 500.

**State its limits in the code, not only here.** The audit is explicit that this
guard catches Eloquent relationship lazy loading only — it does not catch full
scans, bad join order, correlated subqueries, repeated scalar queries, or large
result sets, and **it would not have caught the audit's own headline finding**,
because `roles()->whereKey(...)->exists()` is an explicit relationship query.
A comment claiming broader protection than the mechanism provides is this
repository's most frequent defect.

**Done when**

The guard is on for local and testing and off in production · the full suite
passes with it enabled, or every violation it surfaces is fixed rather than
exempted · **mutation-proved**: removing a required eager load makes a covering
test fail with `LazyLoadingViolationException` · any exception is narrow,
justified in place, and the guard is never globally disabled · `composer verify`
green.

### Task 9 — Identifier codes
**Owner: Claude · `p35/t09-identifier-codes` · depends on nothing**

**File scope**
- `app/Domain/Enrollment/Support/IdentifierCode.php` — **new**; the Enrollment-domain generator
- `app/Domain/Enrollment/Filament/Resources/StudentResource/Pages/CreateStudent.php`
- `app/Domain/Enrollment/Filament/Resources/BatchResource/Pages/CreateBatch.php`
- `app/Domain/Finance/Filament/Pages/EnrollAndCollect.php` — `createStudent()` at `:1161`, **the second student writer**
- `app/Domain/Enrollment/Filament/Resources/StudentResource.php`, `BatchResource.php`, `CourseResource.php` — the form fields
- `lang/en/enrollment.php`, `lang/ar/enrollment.php`
- `docs/superpowers/specs/2026-07-20-training-center-dashboard-design.md` — §6 only, the two column descriptions
- `tests/Feature/Enrollment/IdentifierCodeTest.php` — **new**
- **No migration.** See below.
- **Joins:** `lang/en/enrollment.php` with T07 — **T09 runs first**; system design §6.

**Does**

**Student and batch codes become auto-generated in a fixed readable format.
Course codes stay manual, with a suggestion.** The owner's decision, reversing an
assumption never put to them: the justification for manual codes existed only as a
form comment, and system design §6 merely lists `student_code (unique)` with no
reasoning at all.

Course codes stay manual because `WELD-101` means something — staff say it on the
phone and it is printed in brochures. `CRS-2026-000003` would destroy that.

**THE COLUMNS STAY `NOT NULL UNIQUE`.** Round 1 scoped a migration making them
nullable, which weakens the exact invariant it told the task to copy.
`Reference`'s docblock records that nullability was considered and rejected: the
row is inserted carrying a **unique placeholder**, updated to its real value
inside the same transaction, "so no other connection ever observes a placeholder,
and the column keeps NOT NULL UNIQUE the whole way through". That is the proven
mechanism and this task reuses its shape. **No migration is needed or permitted.**

**A new generator, not an extension of `Reference`.** `Reference::format()`
accepts only `ENR`, `CHG` and `RCT` and lives in Finance; student and batch codes
are Enrollment's. `IdentifierCode` mirrors its approach — derive from the row id
after insert, never `MAX(code)+1`, which is racy under concurrent creation.

**The format is decided here, not at implementation time:**

| | Format | Year source |
|---|---|---|
| Student | `STU-{year}-{id padded to 6}` | the row's `created_at` |
| Batch | `BAT-{year}-{id padded to 6}` | the row's `created_at` — **not `start_date`, which is nullable** |

**Override policy, decided:** the form field stays editable. A centre importing
existing records must be able to keep the number already on the paper file, which
is the one case where the manual-code reasoning was genuinely right. Left blank,
the code is generated; typed, the typed value stands and uniqueness still applies.

**Three creation paths, all in scope.** There are no "Actions that create students
and batches" — round 1 invented them. The real writers are `CreateStudent`,
`CreateBatch`, and `EnrollAndCollect::createStudent()`. **Generation belongs in
one place all three call**, so a fourth writer added later cannot silently skip
it.

**Done when**

A student and a batch created through **each** of the three paths receives a code
without anyone typing one · both columns remain `NOT NULL UNIQUE` and no migration
exists in the diff · a blank field generates and a typed value is preserved · a
concurrency test proves two simultaneous creations cannot collide, demonstrated
rather than argued · the format and the override policy are stated in system
design §6 · existing rows are untouched · `composer verify` green.

machine has no `phpredis` extension, no `predis`, and nothing listening on 6379.

**The dashboard is the security surface, not the recorder.** Pulse's slow-query
card shows query text, and its usage cards show which users did what. It must be
gated behind an explicit authorization check, and that gate must be tested by a
user who should not pass it — not merely declared.

**Sampling and retention are decisions, not defaults to accept.** Pulse records
continuously; state the sample rate and the trim schedule so the tables cannot
grow without bound on a small VPS.

**Done when**

Pulse is installed and recording · slow queries are captured with a **stated**
threshold · the dashboard refuses an authenticated user without the gate, proved
by a test that fails if the gate is removed · sample rate and retention are stated
and applied · no Pulse route is reachable unauthenticated · §11 records what runs
in production · `composer verify` green.

### The alerting gap, recorded rather than scoped as done

**Neither tool alerts on response degradation.** Pulse has no alerting at all — it
is a dashboard. Horizon notifies only on queue wait thresholds.

The owner asked for "alerts on queue backlog and response degradation". T10b
delivers the first. **The second is not delivered by this plan**, and saying
otherwise would be a Done-when the code cannot meet.

Closing it needs a third thing — an error/performance service such as Sentry, or
alerting from the hosting panel — and that is a decision to take once a deployment
exists and T11's baseline says what a degraded response actually looks like.

### Task 11 — Load-test baseline
**Owner: Codex · `p35/t11-load-baseline` · depends on T01, T05**

**File scope**
- `tests/Load/` — **new**; k6 scripts and their fixtures
- `docs/superpowers/specs/2026-07-20-training-center-dashboard-design.md` — §10 only
- **Joins:** system design §10.

**Does**

A repeatable baseline for the flows that matter: login, student search,
enrol-and-collect, the reports, and receipt download.

**Depends on T01 and T05 for a reason.** Running a baseline against
`QUEUE_CONNECTION=database` measures a configuration production will not use, and
running the reports flow before T05's payment-heavy fixture exists measures the
empty-allocation case the audit already warned cannot be projected forward.

**A baseline is a measurement, not a gate.** This task does not fail a build on a
number. It produces figures the owner can set targets against — which is T12's
job, and T12 needs these numbers to exist first.

**The execution model is specified here, because round 1 left it unsafe.**

- **The target is disposable and resettable, and it is never a developer or
  production database.** Enrol-and-collect writes append-only finance and activity
  facts; a load run against a shared database permanently pollutes both.
- **The dataset comes from T05's command**, invoked by name. This task does not
  reimplement seeding.
- **Filament flows are Livewire, not plain HTTP.** State which is used — k6
  browser, or an explicitly maintained HTTP/Livewire protocol harness — and accept
  that the second needs updating when Filament changes.
- **Authenticated sessions and CSRF are prepared once**, not benchmarked.
- **Filament's login self-throttles at 5 attempts per minute.** Logging in per
  virtual user would benchmark the rate limiter and nothing else. Establish
  sessions out of band.
- **The target's real driver configuration is verified**, not assumed from
  `.env.example`. T01 changing an example file does not prove the target uses
  Redis.
- Credentials and secrets never enter the committed scripts.

**Done when**

The scripts run against a stated disposable target and are re-runnable by someone
who did not write them · each flow reports p95 latency, error rate and throughput
· the dataset is built by T05's command at a stated volume · the target's actual
queue, cache and session drivers are recorded alongside the results · results are
committed as a dated baseline, not only pasted into a PR · §10 says where the
scripts live and when to re-run them · `composer verify` green.
