# Phase 3.5 — Hardening and Owner Feedback Implementation Plan

**Status: DRAFT, round 3 — seven P1 blockers from round 2 corrected. No task may begin until this merges green.**

## What three review rounds found, and the rule that follows

The same author error, five times: **a change was scoped against a documented
invariant without reading the file that documents it.**

- Round 1 — §4's "Sessions: database-backed", and `StudentPaymentHistory`'s "no
  period filter".
- Round 2 — `WageCostReport`, whose opening docblock is headed *"THE TRAP THIS
  CLASS EXISTS TO AVOID"* and warns against exactly the change round 2
  instructed; and `Reference`'s audit-log warning, eight lines below the
  placeholder text round 2 did read.
- Round 2 also produced a **confidently wrong inventory**: two of T03's twelve
  classifications were wrong in opposite directions — one already-bounded site
  marked broken, one unbounded site marked safe.

**The rule, for this plan and the phase-4 plan after it:** before a task's scope
is written, the full docblock of every file it touches is read, and every
classification row carries the evidence that justifies it rather than a verdict.
A wrong inventory is more dangerous than a deferred one, because the next reader
does not re-check it.

Both owner decisions are resolved for this plan's purposes: there is no launch
date but readiness is required (Wave 6), and the expenses question no longer
gates anything here because the reports rework moved to the design phase.

**Goal:** Close the gap between what the system does and what it was designed to
do, and act on the owner's first review of the running application — before
phase 4 adds the public site and the Arabic pass on top.

**Why this is not phase 4.** System design §2 already defines phase 4 as "Public
site and Arabic — landing pages, course listings, contact, and the full
bilingual pass", and §13 records a limitation phase 4 must close. The work here
is different in kind: it is hardening, drift-closing and owner feedback, and
several items block go-live. Folding it into phase 4 would queue launch-blocking
work behind a bilingual pass.

**Where the work came from.** Three sources, and they are kept distinguishable
because they carry different evidence:

- **P3-T15's performance audit** (`docs/reviews/2026-09-06-performance-audit.md`),
  which measured two Medium findings and deliberately deferred implementation.
- **The owner's review of the running application**, gathered 2026-09-06/07.
  Some of it contradicts assumptions that were never put to the owner.
- **Drift found while investigating those**, most of it doc-versus-code.

**Tech stack:** Laravel 13.30.1, Filament 5.7.8, `spatie/laravel-permission`

System design **§12 explicitly lists "Expense tracking beyond staff wages" as out
of scope.** The owner has asked for rent and similar costs to be recorded and to
reach the Profit report.

Profit page cannot be drawn without knowing whether overheads exist, so this
decision wants settling before the design phase begins rather than before this
plan does.

Also open if approved: is the category a free-text reason, a fixed enum, or a
managed lookup table? It changes the schema, and it changes what a designer has
to lay out.

### Decision 2 — launch date: ANSWERED

"there is no deploy launch date but we need to be ready."

That is not the same as "later". It means the readiness work is real work with no

### Task 1 — Queue on Redis, and the session lifetime drift
**Owner: Codex · `p35/t01-redis-defaults` · depends on nothing**

**File scope**
- `.env.example`
- `docs/superpowers/specs/2026-07-20-training-center-dashboard-design.md` — §11 only
- `tests/Feature/Tooling/ProductionDefaultsTest.php` — **new**
- **Joins no seam.**

**Does**

**Round 1 got this wrong and the correction is the task.** Round 1 changed
`SESSION_DRIVER` to Redis and called it drift-closing. System design **§4 line 89
says "Sessions: database-backed, 8-hour idle timeout"** — an authoritative
decision this task does not own. §11 assigns **only the queue** to Redis. Redis
cache was never in either document.

So the scope is now three separate things, correctly labelled:

1. **`QUEUE_CONNECTION=redis`** — the genuine design requirement, §11.
2. **`SESSION_LIFETIME=120` → `480`** — **the real drift, which round 1 walked
   past while inventing a different one.** §4 promises an eight-hour idle
   timeout; the shipped example gives two hours. Sessions stay
   `SESSION_DRIVER=database`.
3. **Cache stays `database`.** Redis cache is a new operational choice, not a
   documented requirement, and this plan will not smuggle one in as drift. If it
   is wanted it needs its own owner decision.

**Redis is not present in this development environment** — no `phpredis`
extension, no `predis` in `composer.json`, nothing listening on 6379, while
`.env.example` already names `REDIS_CLIENT=phpredis`. The production VPS gets
Redis from Ploi. So the example file must make the fallback explicit rather than
handing a fresh clone a default that cannot connect.

**Done when**

`.env.example` sets the queue to Redis and states the database fallback in the
same file · `SESSION_LIFETIME` is 480 and sessions remain database-backed · the
cache driver is unchanged and that is stated as deliberate · a test asserts the
example file's drivers and lifetime, so the next drift fails a run rather than
reaching a deployment · §11 records which driver production uses and what happens
without Redis · the local `.env` is untouched · `composer verify` green.

### Task 2 — The super-admin role-id lookup
**Owner: Claude · `p35/t02-superadmin-role-id` · depends on nothing**

**File scope**
- `app/Domain/Staff/Support/SuperAdminRoleId.php` — **new**; the resolver
- `app/Models/Role.php` — `superAdminId()` delegates to it
- `app/Providers/AppServiceProvider.php` — **seam**; `$this->app->scoped(SuperAdminRoleId::class)`
- `tests/Feature/Staff/UserResourceQueryCountTest.php` — **new**
- `tests/Feature/Staff/SuperAdminRoleIdLifecycleTest.php` — **new**

**Does**

`Role::superAdminId()` runs a fresh `SELECT` on `name` + `guard_name` every call.
It is called from `User::isSuperAdmin()`, which the User policy calls per row for
row-action visibility. The audit measured 28 of these on a 10-row page, half of
the 56 repeated rank statements.

**Never cache the User pivot result.** `User::isSuperAdmin()`'s own docblock
records why the fresh id-based lookup exists: a stale in-memory roles relation
once let the last super admin be deleted. The Actions must stay
self-authorizing against current database state. Only the *role id* is memoized,
and the role id is not the authorization read.

**Cache lifetime is a requirement, not an assumption** — this is P3-T15's
re-review point and it is the hard part of this task. Prove the memo cannot leak
across HTTP requests, queue jobs, or long-lived workers, and account for
bootstrap and seeding paths, where the canonical role is created.

**Done when**

**The mechanism is `$this->app->scoped()`, named here rather than chosen on the
branch.** A `static` property on `Role` survives between jobs in a long-lived
queue worker — the exact leak this task exists to prevent. Laravel rebuilds
`scoped` bindings per request **and** between queued jobs, which is the lifecycle
the obligation requires. `Role::superAdminId()` delegates to the resolver so no
caller changes, and **it is a scoped binding, not a singleton** — round 2 called
it a singleton, which is the binding that would leak.

**Done when**

`UserResourceQueryCountTest` drives the real `ListUsers` component and pins the
statement count · the count falls by the role-id lookups and the pivot `exists()`
reads remain uncached · **mutation-proved both ways**: removing the binding
regresses the count, and changing a user's roles before an Action still causes the
Action to authorize against current state · `SuperAdminRoleIdLifecycleTest` proves
**a same-worker two-job case** does not reuse the first job's value, and **a
missing-role-then-seeded case** does not cache a null into a permanent false ·
`composer verify` green.

### Task 4 — Non-production lazy-loading guard
**Owner: Claude · `p35/t04-lazy-loading-guard` · depends on T02** — both write `AppServiceProvider`

**File scope**
- `app/Providers/AppServiceProvider.php` — **seam**; sole writer
- `tests/Feature/Tooling/LazyLoadingGuardTest.php` — **new**
- **Joins:** `AppServiceProvider`.

**Does**

`Model::preventLazyLoading(! $this->app->isProduction())`, enabled for local and
testing and left off in production initially. An unexpected lazy load should fail
in development and CI, not turn a public request into a 500.

**State its limits in the code, not only here.** The audit is explicit that this
guard catches Eloquent relationship lazy loading only — it does not catch full
scans, bad join order, correlated subqueries, repeated scalar queries, or large
result sets, and **it would not have caught the audit's own headline finding**,
because `roles()->whereKey(...)->exists()` is an explicit relationship query.
A comment claiming broader protection than the mechanism provides is this
repository's most frequent defect.

**Done when**

The guard is on for local and testing and off in production · the full suite
passes with it enabled, or every violation it surfaces is fixed rather than
exempted · **mutation-proved**: removing a required eager load makes a covering
test fail with `LazyLoadingViolationException` · any exception is narrow,
justified in place, and the guard is never globally disabled · `composer verify`
green.

**Owner: Codex · `p35/t05-outstanding-query-plan` · depends on nothing**

**Does**

Two defects, both confirmed in cross-review of the audit:

`asOf()` calls `selectRaw(ChargeBalance::outstandingSql())` and then
`whereRaw(ChargeBalance::outstandingSql().' > 0')` — the correlated expression is
written twice, producing two dependent subqueries per charge.

It calls `joinCatalogueTo(..., [DIMENSION_COURSE])`, which joins `enrollments`,
`batches` and `courses` and projects course columns. The row map consumes six
fields and the string `course` appears nowhere else in the file. The join is dead
weight.

**Build the payment-heavy fixture first, and treat it as the deliverable.** The
audit's 4,000-row timings ran with **zero allocations** — the cheapest possible
case for the very subqueries this task is about, which is why its own re-review
calls the number a lower bound that must not be projected forward. Optimising
against that baseline would be optimising against a measurement that cannot show
the defect.

`ChargeBalance` remains the sole balance definition. No balance may be stored.

**The dataset is a command, and it must refuse to run where it could do harm.**
Round 1 scoped the fixture inside the test, where the Pest transaction rolls it
back and it can never seed the target T11 consumes. Round 2 made it a command but
called the target "disposable" in prose. **A command that writes thousands of
payments, tenders and allocations needs a boundary, not an adjective** —
enrol-and-collect writes append-only finance and activity facts, and one mistyped
Artisan invocation is irreversible.

```
php artisan seed:performance-dataset --profile=small|medium --confirm-database=<name>
```

- **Refuses when `app()->isProduction()`**, unconditionally.
- **Refuses unless `--confirm-database` exactly matches the connected database
  name**, so the target is named twice by different means.
- **Refuses any database absent from the `config/performance.php` allowlist** —
  the test database and one explicitly named performance database.
- Profiles are fixed and deterministic, with a fixed seed: `small` = 1,000
  charges / 2,000 allocations; `medium` = 4,000 charges / 8,000 allocations.
- Re-running truncates its own data first, so successive results are comparable.

T11 invokes this command by name and does not reimplement seeding.

**Done when**

The command exists with all three refusals, **each proved by a test asserting the
refusal rather than the success path** · before-and-after timings and `EXPLAIN`

duplicated aggregate is resolved without a second definition of balance ·

### Task 8 — Wage cost and profit over a range of months
**Owner: Codex · `p35/t08-month-range-reports` · depends on T03**

**File scope**
- `app/Domain/Finance/Support/MonthRange.php` — **new**
- `app/Domain/Finance/Reports/WageCostReport.php`
- `app/Domain/Finance/Reports/ProfitReport.php`
- `app/Domain/Finance/Exports/ReportDataBuilder.php` — `:184` and `:201`
- `app/Domain/Finance/Filament/Pages/Reports/ReportPage.php` — **seam**; after T03
- `tests/Feature/Finance/Reports/WageCostReportTest.php` — existing
- `tests/Feature/Finance/Reports/ProfitReportTest.php` — existing
- `tests/Feature/Finance/Reports/ReportExportTest.php` — existing
- `tests/Feature/Finance/Reports/ReportPageAccessTest.php` — existing
- **Joins:** `ReportPage.php` with T03.

**Does**

**Round 2 instructed the exact change these classes exist to refuse.**
`WageCostReport`'s docblock is headed *"THE TRAP THIS CLASS EXISTS TO AVOID:
`posting_period_start` IS A LOCAL DATE, NOT AN INSTANT, AND `ReportPeriod` IS
BUILT FOR INSTANTS"*. `ProfitReport`'s says its signature is `forMonth(int, int)`
"BECAUSE THE TWO HALVES ALIGN THEMSELVES BY CONSTRUCTION" — it builds
`ReportPeriod::month()` internally for the revenue half and hands the same two
integers to the wage half, so no caller can pass March to one side and February to
the other. **Neither may take a `ReportPeriod`.**

**The semantic question round 2 left open, answered: whole local months only.**
`FinalizePayrollRunAction` already normalizes `posting_period_start` to the first
of a month. A 15 March–15 April filter has no meaning against that storage, and
prorating a finalized posting would invent a figure the payroll run never
produced. **The UI accepts a from-month and a to-month.**

`MonthRange` is a value object over `(fromYear, fromMonth, toYear, toMonth)` that
yields the `(int $year, int $month)` pairs between them, inclusive. It is **not** a
`ReportPeriod` and never converts to instants.

```php
WageCostReport::forMonths(MonthRange $range): Collection
WageCostReport::totalForMonths(MonthRange $range): Money
ProfitReport::forMonths(MonthRange $range): array
```

Each iterates the range and composes the existing per-month results, so the
by-construction alignment `ProfitReport` protects is preserved: every month is
still `ReportPeriod::month($y, $m)` for revenue and the same two integers for
wages. `forMonth()` remains and delegates to a one-month range, so no existing
caller breaks.

**The other five reports are unchanged**, and Student Payment History especially:
its docblock says "every bill raised against them and every receipt they were
handed, **with no period filter**", and "'Every' is load-bearing". Phase-2 §8
agrees. **All-time is not in this task** — see the deferred table.

**Done when**

Wage cost and profit accept a `MonthRange`, and a test asserts `ReportPeriod`
never reaches `posting_period_start` · a range spanning a year boundary is
correct, tested at December–January · `forMonth()` still works and is proved equal
to a one-month range · the export and snapshot paths carry the range with
unchanged meaning · **Student Payment History is untouched, and a test asserts it
still returns every bill and every receipt** · the four other reports are
confirmed unchanged · `composer verify` green.

**Does**

Student and batch codes become generated; course codes stay manual with a
suggestion. The owner's decision, reversing an assumption never put to them — the
justification for manual codes existed only as a form comment, and §6 lists
`student_code (unique)` with no reasoning at all.

**THE PLACEHOLDER MECHANISM IS ABANDONED, AND ROUND 2'S REVIEW IS WHY.** Round 2
told this task to copy `Reference`'s placeholder-in-transaction. Two measured
facts make that unusable here:

- `PLACEHOLDER-` plus a UUID is **48 characters**. `students.student_code` is
  `varchar(30)` and `batches.code` is `varchar(40)`. **It fits neither.**
- `student_code` is in `Student::auditedAttributes()` and `code` is in
  `Batch::auditedAttributes()`. `Reference.php:39-48` warns explicitly that a
  transaction does **not** stop model events logging the placeholder — Finance
  escapes it only because its references are excluded from audited attributes.
  Copying the shape here would write an internal placeholder into an append-only
  log, or cost the auditing of manual overrides.

**Use `CertificateReference`'s proven pattern instead: a random suffix, the
existing unique index, and a bounded retry.** No second write, so no placeholder
ever exists, the audit log sees only real codes, the columns stay `NOT NULL
UNIQUE`, and **no migration is needed.**

| | Format | Fits |
|---|---|---|
| Student | `STU-{year}-{6}` | 15 chars in `varchar(30)` |
| Batch | `BAT-{year}-{6}` | 15 chars in `varchar(40)` |

The suffix draws from `CertificateReference::ALPHABET` — uppercase without `0/O`
and `1/I/L`, because these are read off paper and typed back. The year is the
row's `created_at`, **not `start_date`, which is nullable on batches**. Retries
are bounded and exhaustion throws `IdentifierCodeExhaustedException`, exactly as
`IssueStudentCertificateAction` handles reference exhaustion.

**One writer, three callers.** `AssignIdentifierCodeAction` owns generation and
retry; `CreateStudent`, `CreateBatch` and `EnrollAndCollect::createStudent()` call
it. An architecture test asserts nothing else assigns these columns, so a fourth
writer added later cannot silently skip it.

**Override:** the field stays editable. Left blank it is generated; typed, the
typed value stands and uniqueness still applies — importing an existing centre's
records is the one case where the manual-code reasoning was right. **A typed
override is an ordinary audited attribute**, which is precisely what the
placeholder approach would have cost.

**Course codes** gain a `placeholder()` showing an example shape. It suggests and
never fills, so nothing is submitted the operator did not type.

**Done when**

Each of the three creation paths yields a code with nothing typed · both columns
remain `NOT NULL UNIQUE` and **no migration appears in the diff** · a blank field
generates and a typed value is preserved · **the activity log for a created
student contains a real code and never a placeholder**, asserted directly ·
`IdentifierCodeConcurrencyTest` proves two simultaneous creations cannot collide
and that exhaustion throws rather than returning a duplicate ·
`IdentifierCodeArchTest` proves only the Action assigns these columns · the
format, the alphabet and the override policy are stated in §6 · existing rows are
untouched · `composer verify` green.
