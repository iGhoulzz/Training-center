# Phase 3.5 — Hardening and Owner Feedback Implementation Plan

**Status: DRAFT — awaiting Codex's plan review. No task may begin until this merges green.**

Both owner decisions are resolved for this plan's purposes: there is no launch
date but readiness is required (Wave 6), and the expenses question no longer
gates anything here because the reports rework moved to the design phase.

**Goal:** Close the gap between what the system does and what it was designed to
do, and act on the owner's first review of the running application — before
phase 4 adds the public site and the Arabic pass on top.

**Why this is not phase 4.** System design §2 already defines phase 4 as "Public
site and Arabic — landing pages, course listings, contact, and the full
bilingual pass", and §13 records a limitation phase 4 must close. The work here
is different in kind: it is hardening, drift-closing and owner feedback, and
several items block go-live. Folding it into phase 4 would queue launch-blocking
work behind a bilingual pass.

**Where the work came from.** Three sources, and they are kept distinguishable
because they carry different evidence:

- **P3-T15's performance audit** (`docs/reviews/2026-09-06-performance-audit.md`),
  which measured two Medium findings and deliberately deferred implementation.
- **The owner's review of the running application**, gathered 2026-09-06/07.
  Some of it contradicts assumptions that were never put to the owner.
- **Drift found while investigating those**, most of it doc-versus-code.

**Tech stack:** Laravel 13.30.1, Filament 5.7.8, `spatie/laravel-permission`

## Two owner decisions gate part of this plan

**Neither is mine to make, and two tasks below cannot be scoped until they are
answered.**

### Decision 1 — expense tracking

System design **§12 explicitly lists "Expense tracking beyond staff wages" as out
of scope.** The owner has asked for rent and similar costs to be recorded and to
reach the Profit report.

The owner may change the scope — it is their system. But CLAUDE.md requires §12
to be checked before adding anything not asked for, so this needs a deliberate
spec amendment rather than a task that quietly overrides it.

If approved, it is a domain area rather than a screen: a table, a category
concept, a write Action, permissions, and a change to what "Profit" computes.

**No task in this plan is blocked on it**, and that is deliberate. The reports UI
rework has moved to the owner's planned design phase, so nothing here is waiting
on the answer. What the answer does affect is **that** phase: a design for a
Profit page cannot be drawn without knowing whether overheads exist, so this
decision wants settling before the design phase begins rather than before this
plan does.

Also open if approved: is the category a free-text reason, a fixed enum, or a
managed lookup table? It changes the schema, and it changes what a designer has
to lay out.

### Decision 2 — launch date: ANSWERED

**There is no target date, and readiness is still required.** The owner's words:
"there is no deploy launch date but we need to be ready."

That is not the same as "later". It means the readiness work is real work with no
deadline attached, so it belongs in Wave 6 below rather than in a checklist that
nobody owns. What it removes is the sequencing pressure: nothing here has to be
rushed to hit a date, and a readiness task that finds a problem is allowed to
take the time to fix it.

One item genuinely cannot become a task — see Wave 6 — because it is hosting-panel
configuration rather than anything that can be reviewed as a diff.

### Task 1 — Redis as the production default
**Owner: Codex · `p35/t01-redis-defaults` · depends on nothing**

**File scope**
- `.env.example`
- `docs/superpowers/specs/2026-07-20-training-center-dashboard-design.md` — §11 only

**Does**

The design already says Redis. System design §2's hosting row says the VPS
"provides queue workers, Redis, and scheduled tasks", and §11 says "Queue workers
via Redis, managed by the hosting panel". The shipped `.env.example` says
`CACHE_STORE=database`, `SESSION_DRIVER=database`, `QUEUE_CONNECTION=database`.

**This task closes a drift, it does not make a new decision.** Database stays
configured and supported as the fallback — a single-VPS deployment with no Redis
must still boot.

**Done when**

`.env.example` defaults to Redis for cache, session and queue, with the database
fallback documented in the same file · §11 states which driver production uses
and what the fallback is · a test asserts the example file's drivers, so the next
drift fails a run rather than reaching a deployment · the local `.env` is
untouched · `composer verify` green.

### Task 2 — The super-admin role-id lookup
**Owner: Claude · `p35/t02-superadmin-role-id` · depends on nothing**

**File scope**
- `app/Models/Role.php` — **seam**; sole writer
- `tests/Feature/Staff/UserResourceQueryCountTest.php` — **new**
- **Joins no seam.**

**Does**

`Role::superAdminId()` runs a fresh `SELECT` on `name` + `guard_name` every call.
It is called from `User::isSuperAdmin()`, which the User policy calls per row for
row-action visibility. The audit measured 28 of these on a 10-row page, half of
the 56 repeated rank statements.

**Never cache the User pivot result.** `User::isSuperAdmin()`'s own docblock
records why the fresh id-based lookup exists: a stale in-memory roles relation
once let the last super admin be deleted. The Actions must stay
self-authorizing against current database state. Only the *role id* is memoized,
and the role id is not the authorization read.

**Cache lifetime is a requirement, not an assumption** — this is P3-T15's
re-review point and it is the hard part of this task. Prove the memo cannot leak
across HTTP requests, queue jobs, or long-lived workers, and account for
bootstrap and seeding paths, where the canonical role is created.

**Done when**

A query-count test drives the real `ListUsers` component and pins the statement
count for a populated page · the count falls by the role-id lookups and the
pivot `exists()` reads remain · **mutation-proved both ways**: removing the memo
regresses the count, and changing a user's roles before an Action still causes
the Action to authorize against current state · a test demonstrates the memo does
not survive across simulated request boundaries · `composer verify` green.

## Wave 2

### Task 3 — Bound every unbounded option list
**Owner: Codex · `p35/t03-bounded-option-lists` · depends on nothing**

**File scope**
- `app/Domain/Finance/Filament/Pages/Reports/ReportPage.php` — **seam**; sole writer this wave, and **T08 must not start until this merges**
- `app/Domain/Staff/Filament/Resources/ActivityResource.php`
- `tests/Feature/Finance/ReportFilterBoundsTest.php` — **new**
- **Joins:** `ReportPage.php`.

**Does**

`ReportPage.php:134` builds the Student Payment History filter with an unbounded
`Student::withTrashed()->orderBy(...)->get()->mapWithKeys(...)`, selecting
`students.*` when the label needs four columns. The audit measured 60–93 ms and
6 MiB at 2,000 students, on every render, whether or not a student is chosen.
`ActivityResource.php:187` has the same shape for causer options, and portal
accounts share the users table.

**Start with a repo-wide sweep, not with these two.** The owner's report of this
was general — "remove unbounded `->get()` option lists" — and the audit found two
by inspection. Find them all first and report the list; a task that fixes the two
already known and leaves a third is the same defect with better paperwork.

Preserve `withTrashed()` so historical students and staff remain reportable.

**Done when**

The sweep is reported, with every unbounded option list named and each one either
fixed or explicitly justified · the fixed ones use server-side search with a
selected-option label resolver and select only the label columns · a test asserts
bounded query and payload behaviour at 2,000 students, and **fails if the
unbounded shape returns** · `composer verify` green.

### Task 4 — Non-production lazy-loading guard
**Owner: Claude · `p35/t04-lazy-loading-guard` · depends on nothing**

**File scope**
- `app/Providers/AppServiceProvider.php` — **seam**; sole writer
- `tests/Feature/Tooling/LazyLoadingGuardTest.php` — **new**
- **Joins:** `AppServiceProvider`.

**Does**

`Model::preventLazyLoading(! $this->app->isProduction())`, enabled for local and
testing and left off in production initially. An unexpected lazy load should fail
in development and CI, not turn a public request into a 500.

**State its limits in the code, not only here.** The audit is explicit that this
guard catches Eloquent relationship lazy loading only — it does not catch full
scans, bad join order, correlated subqueries, repeated scalar queries, or large
result sets, and **it would not have caught the audit's own headline finding**,
because `roles()->whereKey(...)->exists()` is an explicit relationship query.
A comment claiming broader protection than the mechanism provides is this
repository's most frequent defect.

**Done when**

The guard is on for local and testing and off in production · the full suite
passes with it enabled, or every violation it surfaces is fixed rather than
exempted · **mutation-proved**: removing a required eager load makes a covering
test fail with `LazyLoadingViolationException` · any exception is narrow,
justified in place, and the guard is never globally disabled · `composer verify`
green.

## Wave 3

### Task 5 — Outstanding Aged query plan
**Owner: Codex · `p35/t05-outstanding-query-plan` · depends on nothing**

**File scope**
- `app/Domain/Finance/Reports/OutstandingAgedReport.php`
- `app/Domain/Enrollment/Services/EnrollmentQueryService.php`
- `tests/Feature/Finance/OutstandingAgedPerformanceTest.php` — **new**
- **Joins no seam.**

**Does**

Two defects, both confirmed in cross-review of the audit:

`asOf()` calls `selectRaw(ChargeBalance::outstandingSql())` and then
`whereRaw(ChargeBalance::outstandingSql().' > 0')` — the correlated expression is
written twice, producing two dependent subqueries per charge.

It calls `joinCatalogueTo(..., [DIMENSION_COURSE])`, which joins `enrollments`,
`batches` and `courses` and projects course columns. The row map consumes six
fields and the string `course` appears nowhere else in the file. The join is dead
weight.

**Build the payment-heavy fixture first, and treat it as the deliverable.** The
audit's 4,000-row timings ran with **zero allocations** — the cheapest possible
case for the very subqueries this task is about, which is why its own re-review
calls the number a lower bound that must not be projected forward. Optimising
against that baseline would be optimising against a measurement that cannot show
the defect.

`ChargeBalance` remains the sole balance definition. No balance may be stored.

**Done when**

A reusable payment/allocation fixture exists and is used here · before-and-after
timings and `EXPLAIN` output are reported against it, not against the empty
dataset · the catalogue join is gone or narrowed to the enrolment identity
actually used · the duplicated aggregate is resolved without a second definition
of balance · `composer verify` green.

### Task 8 — Report period filters
**Owner: Codex · `p35/t08-report-periods` · depends on T03**

**File scope**
- `app/Domain/Finance/Filament/Pages/Reports/ReportPage.php` — **seam**; T03 must be merged first
- `app/Domain/Finance/Support/ReportPeriod.php`
- `tests/Feature/Finance/ReportPeriodFilterTest.php` — **new**
- **Joins:** `ReportPage.php`.

**Does**

`ReportPeriod` already supports `month()`, `day()` and `between()`. The engine is
not the limitation — `filterFields()` is. Wage cost and Profit expose a month
only and cannot span a quarter; Student Payment History has no period filter at
all; nothing offers all-time.

Outstanding Aged and Daily Tender keep their single date. Those two are genuinely
point-in-time — as-of and per-day — and must not be converted to ranges.

**Done when**

Every report exposes a period appropriate to its meaning, with the two
point-in-time reports unchanged and that decision stated · an all-time option
exists and is bounded so it cannot be an unbounded scan by accident · Student
Payment History gains a period filter · `composer verify` green.

## Wave 5

### Task 9 — Identifier codes
**Owner: Claude · `p35/t09-identifier-codes` · depends on nothing**

**File scope**
- `database/migrations/` — **new**, nullability of `students.student_code` and `batches.code`
- `app/Domain/Enrollment/Actions/` — the Actions that create students and batches
- `app/Domain/Enrollment/Filament/Resources/StudentResource.php`, `BatchResource.php`, `CourseResource.php`
- `lang/en/enrollment.php`
- **Joins:** `lang/en/enrollment.php`.

**Does**

**Student and batch codes become auto-generated in a fixed readable format.
Course codes stay manual, with a suggestion.** That is the owner's decision, and
it reverses an assumption that had never been put to them: the justification for
manual codes existed only as a form comment, and the design spec merely lists
`student_code (unique)` with no reasoning.

Course codes stay manual because `WELD-101` means something — staff say it on the
phone and it is printed in brochures. `CRS-2026-000003` would destroy that.

**Follow `Reference::format()`, do not invent a second mechanism.** It derives
`{PREFIX}-{year}-{id padded to 6}` from the row id after insert, precisely
because a `MAX(code)+1` lookup is racy under concurrent creation.

**Done when**

A student and a batch created through the panel receive a code without anyone
typing one · the format is stated in the spec, not only in code · concurrent
creation cannot produce a collision, and that is demonstrated rather than argued
· whether an override remains for importing an existing centre's records is
decided and stated · existing rows are untouched · `composer verify` green.

## What this plan does not cover

**A design phase, planned by the owner, will implement a UI rework against a
prepared design.** These belong to it and are deliberately absent here:

- **The financial reports rework.** The owner's objection stands and is recorded:
  figures are not traceable to the rows behind them, and the terms are undefined
  on screen. "Revenue" means collected rather than billed, and "Profit" is
  revenue minus wages only. Both are correct implementations of definitions the
  page never states, so this is a presentation problem with a domain question
  underneath it — see Decision 1.
- **Visual treatment generally.** T07 in this plan changes what a notification
  *says* and whether it carries an action, because the exception detail is
  already thrown and then discarded. How those notifications look is the design
  phase's call, and T07 must not pre-empt it.

Phase 4's work is unchanged and stays in phase 4: the public site, landing pages,
course listings, contact, and the full bilingual pass. Every catalogue this plan
touches ships with an empty `lang/ar/` counterpart, as phase 3's did.

From system design §12, recorded so they do not reappear as assumptions:
multi-tenancy, attendance tracking, grades, timetabling, online card payments, a
mobile application, public student self-registration, and certificate template
design or printing.
